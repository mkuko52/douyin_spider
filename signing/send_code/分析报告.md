## 2. 参数生成位置（逆向定位）

| 参数组 | 生成位置 | 算法 |
|---|---|---|
| `mobile` / `code` / `type` / `account` | 模块 `86465` 的函数 `c` | `enc(s) = hex(utf8(s) XOR 0x05)` |
| `sign` / `qs` | 模块 `86465` 的函数 `d`（依赖 `l` 排序） | `sha256( params排序前10 + "&" + body排序全部 + "&app_key=" + APP_KEY )`；`qs = enc(前10个键名,逗号连接)` |
| `APP_KEY` | `client-entry~*.js` 配置 | `163e7ce78d58971a41f5b969996d85c2`（aid=6383） |
| `x-tt-passport-aid-sign` | 模块 `370824` | `HMAC(HKDF-Expand(HMAC(ts, appKey)), "aid=…&path=…&ts=…")` |
| `ts` | SDK 常量计算 | 当天 12:00 UTC 的秒级时间戳（**整天不变**） |
| `x-tt-session-dtrait` | `uc-secure-dtrait-core`（87 KB JSVMP 库） | RSA-2048 包 `(AES key‖iv)` + AES-128-CBC 加密设备指纹 payload |
| `a_bogus` | `webmssdk` / `abogus.js` | SM3 派生 + 环境指纹 |
| `fp` / `verifyFp` | cookie `s_v_web_id` | `verify_xxx`，服务端下发，**设备级固定** |
| `p_no` / `p_ts` / `biz_trace_id` | SDK 运行时生成 | 随机 / 时间戳 |
| `msToken` | 响应头 `X-Ms-Token` 或 cookie | 服务端下发 |

## 3. 参数分类：哪些固定、哪些动态

### 3.1 完全固定（SDK 版本常量，永不变）

`passport_jssdk_version=3.4.4` · `passport_jssdk_type=normal` · `is_from_ttaccountsdk=1` ·
`aid=6383` · `language=zh` · `account_app_language=zh-CN` · `is_from_iesaccountsaas=1` ·
`p_ui=2.4.4` · `p_ca=4.0.26` · `p_ca_real=1.0.0.910` · `account_sdk_source=web` ·
`p_js_v=3.4.4` · `p_js_t=pro` · `p_zt=3.3.25` · `p_ver=1.1.3` · `p_ver_real=0` ·
`p_bd=1.0.1.19-fix.01` · `device_platform=web_app` · `web-sdk-version=1`（头）
`request_host=https%3A%2F%2Fwww.douyin.com` · body 的 `is6Digits/mix_mode/fixed_mix_mode`

### 3.2 半固定（按天 / 按设备 / 按会话）

| 参数 | 变化频率 | 来源 |
|---|---|---|
| `ts` | 每天 12:00 UTC 变一次 | 由日期算出 |
| `x-tt-passport-aid-sign` | 随 `ts`，即每天一次 | 由 `ts` 算出 |
| `fp` / `verifyFp` | 每设备一次 | cookie `s_v_web_id` |
| `account_sdk_source_info` | 换机器 / 换指纹浏览器才变 | enc(环境描述 JSON) |
| `qs` | 键名集合固定 → 值固定 | 由前 10 个键名算出 |
| `passport_csrf_token` / `ttwid` / `odin_tt` | 每会话（数天） | 服务端下发 |
| `msToken` | 每会话 / 每次响应刷新 | 响应头 `X-Ms-Token` |

### 3.3 每次请求都变（真正的动态参数）

| 参数 | 生成规则 | 为什么必须现场生成 |
|---|---|---|
| `p_ts` | 当前毫秒时间戳 | 时间窗口校验 |
| `p_no` | 64 位十六进制随机 | **一次性**，用过即废 |
| `biz_trace_id` | 32 位十六进制随机 | 同 `x-tt-passport-trace-id` 头 |
| `sign` | 由上面参数派生 | 随 `p_no/p_ts` 变 |
| `a_bogus` | 由 query + 环境指纹签名 | 每次不同 |
| **`x-tt-session-dtrait`** | 现场采集设备指纹后 RSA+AES 加密 | **复用旧值必被 2156** |
| `x-tt-passport-verify-portrait` | UUID + `.login` | 每次不同 |
| `mobile` / `type`（body） | enc() | 随手机号变 |

> **关键结论**：`dtrait` 是"每次请求现场生成"的。上一轮工作之所以卡住，就是借用了旧
> `dtrait`。本次已做到**每次请求重新在 nv8 里跑核心采集**（见第 5 节）。

```
│   ├── signer_server.mjs    常驻参数服务（JSON-Lines over stdio）

├── runtime/                 venv + node_local（项目自带，不读本机环境变量）
```

### dtrait 现场采集（本次攻破的关键）

`uc-secure-dtrait-core` 是 JSVMP 混淆库，静态读不懂。但它可以在 **nv8**（Node 里的 Edge
运行时）中直接执行并产出设备指纹。踩过的三个坑（已在代码注释中固化）：

1. 核心**在模块加载时**采集并 `console.log('[params]', payload)`；
2. 该日志的 `[params]` 与 payload 是**两个参数**，必须拼起来再解析；
3. 采集是**被请求拦截器触发**的：必须`先替换 window.fetch` → `再 getInstance` → `最后发一个命中路径的请求`。
   顺序错了（先 getInstance 再换 fetch）会把 SDK 的拦截器顶掉，永远采不到。

`nv8` 的存在意义正在于此：核心会读 `navigator` / `screen` / canvas / WebGL 等大量环境特征，
裸 Node 跑必然抛错或降级成错误的指纹——nv8 把这些补成"检测不出来"的程度。

### 分工边界

- **Node**：只生成参数（dtrait payload、a_bogus），**不发任何网络**（fetch 被换成本地 sink）。
- **Python**：独占最终 HTTP 出口，负责组装与发送。

|---|---|---|

| `/passport/web/send_code/` | ✅ | HTTP 200 · `error_code: 2156` |

**逐位一致**（`79c2ed7631a19e3fdb6ddde0887959bcf6773e81b4081db06aca5c94b89f6bbc`）。

**这三条合起来证明了什么：**

1. `sign` / `qs` / `a_bogus` / `x-tt-passport-aid-sign` / `x-tt-session-dtrait` 全部**正确**
   —— 能在受保护的 `/passport/web/*` 端点上拿到 `error_code: 0`。
2. cookie / 会话层（含 `bit_env`、`sdk_source_info`、`bd_ticket_guard_client_data`）也**足够**。
3. 所以 `send_code` 的 `2156` **不是签名或参数问题**，而是**“发短信”这个动作特有的风控策略**；
   而 `/send_activation_code/v2/` 返回的 HTML 引导页说明它还额外要求 `bdms`/`secsdk` 请求级签名。

### 早期（错误）结论中被推翻的部分

| 早期说法 | 实测结果 |
|---|---|
| `Key-Sign-Result: 2` = 签名被拒 | ❌ 成功响应上也是 2，只是常量标记 |
| `sign`/`qs` 与抓包一致但仍 2156 → 说明 HTTP 层之下还有东西 | ⚠️ 抓包样本是**旧会话**的；换成浏览器**现场**会话后，同参数层能打成功 get_qrcode |
| 缺请求级票据签名是 2156 的正解 | ❌ 不成立；真因是端点级风控（发短信） |

仍然成立的排除项：

| 假设 | 结论 |
|---|---|
| 参数算错 | ❌ 排除：现场抓包 `sign`/`qs` 逐位一致，且 get_qrcode 成功 |
| `dtrait` 是旧的 | ❌ 排除：每次现场采集；且该 dtrait 已被服务端接受（get_qrcode error_code 0） |
| cookie 不全 | ❌ 排除：浏览器现场全量 cookie（134 个）+ 自生成参数即成功 |
| 端点差异 | ✅ **真因**：`send_code` / `send_activation_code` 额外要过风控 |

```
body：mix_mode=1&mobile=<enc>&type=3731&is6Digits=1&fixed_mix_mode=1
```

**只有 7 个参数**，且 **没有** `sign` / `qs` / `a_bogus` / `msToken` / `ts` / `fp`，
也没有 `x-tt-session-dtrait` 头。

**③ 站点自己拿到的响应 —— 也不是 JSON**

```
HTTP 200 · content-type: text/html; charset=utf-8 · 10168 字节
```

body 是**安全 SDK 引导页**：

```html
<script src=".../rc-client-security/web/glue/1.0.0.61/sdk-glue.js"></script>
<script>
  var sdkInfo = {
    csrf:         { isLoaded: () => !!window.secsdk,     src: secsdk-lastest.umd.js },
    bdms:         { isLoaded: () => !!window.bdms,       src: bdms.js 1.0.1.15 },
    verifyCenter: { isLoaded: () => !!window.TTGCaptcha, src: sec_sdk_build/4.0.10/captcha/index.js }
  };
  window._SdkGlueInit({ bdms: { aid: 10006, pageId: 31827,
                                paths: { include: ["/get_qrcode"] } } }, sdkInfo);
</script>
```

因为拿到 HTML 而不是 JSON，登录页直接弹 **"网络异常，请稍后重试"**，
而且**没有**任何后续重试请求（`sdk-glue.js`/`bdms.js` 根本没被加载）。

**这组证据的含义（比只看 2156 更硬）**

1. **"发码成功"的标志不是 HTTP 200，而是 JSON。** 拿到 `text/html` 就是被挡了。
2. 当前 SSO 链路端点是 **`/send_activation_code/v2/`**（`aid=24`、`account_sdk_source=sso`），
   **不用** `sign`/`qs`/`a_bogus`，参数层比我们实现的轻得多。
3. 服务端要求客户端先加载 **`sdk-glue` → `bdms` + `secsdk` + `TTGCaptcha`**，
   由它生成**请求级签名头**后重试。这与响应头 `Bd-Ticket-Guard-Key-Sign-Result: 2` 的结论一致。
4. 所以"纯协议直连发码"在当前版本**不可行**：要先过 WAF/VerifyCenter 滑块，
   再过 `bdms`/`secsdk` 请求级签名。浏览器能用，是因为它真的执行了这些 SDK。

## 6.5 最终可用交付形态（2026-09-18 实测成功）

```bash
python main.py --mobile <号码>          # 默认来源就是 browser
```

输出：

```json
HTTP 200
{"data":{"log_id":"…","mobile":"130******00",
         "mobile_ticket":"mobile_ticket_…","retry_time":60},"message":"success"}
```

**运行形态**：全程异步 —— HTTP 出口用 `aiohttp`，浏览器工件用 `playwright.async_api`，
Node 参数服务用 `asyncio.create_subprocess_exec` 常驻子进程；`main.py` 入口 `asyncio.run()`。

**分工**：

- **浏览器**只做**窄工件生成器** —— 打开真实页面，让页面上的 bdms 为我们的 URL 生成 `a_bogus`；
  XHR 在 `send` 处被拦下，**不发任何业务请求**；返回**完整的签名后 URL**
  （bdms 会自补 `msToken`，所以必须用整条 URL 发）。
- **Python 独占 final live egress** —— 真正的发码请求由 `main.py` 发出。

`--abogus-source nv8` 是完全无浏览器路径：参数层全部与抓包逐位一致，
环境值也已与浏览器逐字段对齐（差异 0），但服务端仍拒收 nv8 自产的 `a_bogus`（`2156`）。

## 7. 运行方式

```bash
# 一句跑完全流程（生成参数 -> 请求 -> 打印响应），无需任何控制台输入
python main.py

# 只生成参数，不发请求
python main.py --dry-run

# 换目标号码（覆盖 config.local.json）
python main.py --mobile 139xxxxxxxx

# 离线固定向量
python tests/test_vectors.py

# 想用项目自带运行时（venv + node 都不依赖本机环境变量）
runtime\venv\Scripts\python.exe runtime\bootstrap.py --install   # 只需一次
runtime\venv\Scripts\python.exe runtime\run.py
```

配置写在 `config.local.json`：`mobile` / `cookie_file` / `verify_tls`，命令行参数优先。
`mobile` 缺省是非可投递占位号，所以默认不会给真实用户发短信。

## 8. 边界与合规

- Node 只生成参数、不发网络；Python 独占 HTTP 出口。
- `python main.py` 直接跑完整流程；`--dry-run` 只生成参数不发请求。
- `mobile` 缺省为非可投递占位号；换成真号前请确认那是你自己的号码。
- 该接口会给目标号码发**真实短信**；请只对自己持有的号码使用。
- 连续测试会把风控推高（实测发码也会开始要求验证码），建议控制频率。
